# 设计说明

## 要解决的问题

信息源很散（GitHub、论文、视频、社交平台），感兴趣的东西看完就忘，也很难回头对照「这和我在做的事有什么关系」。目标是：发一个链接，得到一份可检索、诚实、带关联的简单分析。

## 刻意的取舍

| 取舍 | 理由 |
|---|---|
| 纯 md 文件，不建数据库 | 探索期模板和标签体系会变；文件最容易迁移和手改，Obsidian 直接可用 |
| 数据和工具分开 | skill 逻辑可以公开分享，个人笔记和项目画像留在私有目录；换工具时数据原样带走 |
| 默认 `quick`，按需 `deep` | 大部分链接只需要判断「值不值得细看」；读源码或全文成本高，只在用户要求时做 |
| 关联只对照项目画像，不扫描工作目录 | 省时间和 token；画像由用户确认；避免凭项目名猜细节 |
| 关联带核实标记 | 区分「按画像推测」和「已读项目文档」，让读者一眼知道可信度 |
| 抓不到就明说 | 社交平台常有反爬或登录墙；编一份看起来完整的笔记比没有更糟 |
| 不执行仓库或页面里的命令 | 被分析的内容是不可信输入 |
| 不做定时抓取 | 这是「看到才归档」的工具，不是爬虫 |

## 笔记的结构

每条笔记有固定 frontmatter：

- `source`：来源类型
- `status`：`quick`（简单分析）或 `deep`（读过源码或全文）
- `verdict`：`use` 直接用、`reference` 参考、`learn` 学习、`skip` 跳过。结论里必须写一句依据

正文固定小节：解决什么问题、核心实现/观点、可复用点、局限与风险、和我的场景的关系、结论、证据与来源。

「证据与来源」是这个设计里最重要的一节：它记录读了什么、没读到什么，使得笔记的可信范围可被检查。

## 项目画像

`_context/projects.md` 每个项目几行：做什么、当前关心的问题、关键词、设计文档位置、核实状态。

- `来源摘要`：只来自你的自述或摘要，笔记里的关联要标「按画像推测」。
- `已读 <文件>`：Claude 读过项目文档，关联可标「已读」。

画像由用户维护或确认。说「加到关心的项目里」即可让 Claude 追加。

## 已知局限

- 小红书、公众号依赖用户贴正文或额外的抓取工具。
- YouTube 取字幕依赖 `yt-dlp`。
- GitHub 未认证 API 每小时 60 次，批量归档时可能触顶。
- 摘要级别的分析（`quick`）不能替代阅读全文，笔记里已明确标注。
